1. Nombres, Vinculación (Binding), Estructuras de Control y Alcance (Scoping)

1.1 Nombres, Palabras Reservadas e Identificadores

De acuerdo con la especificación de C# (ECMA-334, Cap. 6), los identificadores son sensibles a mayúsculas y minúsculas (case-sensitive), admiten caracteres Unicode de categorías de letras y guion bajo inicial, y distinguen estrictamente entre palabras clave reservadas (class, struct, ref, in, out, switch) y palabras clave contextuales (record, init, var, required). Estas últimas permiten evolucionar la sintaxis del lenguaje sin invalidar identificadores en programas preexistentes.

En el Mini-REPL, el analizador léxico SpanLexer aplica una clasificación determinista sobre cada lexema extraído de ReadOnlySpan<char>: verifica primero operadores y palabras clave del lenguaje RPN (true, false, begin, end), luego literales numéricos enteros/flotantes y, por último, identificadores válidos iniciados en letra o _.

1.2 Tiempos de Vinculación (Binding Times) y Semántica L-value vs. R-value

C# es un lenguaje predominantemente de vinculación estática (en compilación mediante Roslyn), combinando distintos instantes de enlace según la construcción:

  • Tiempo de diseño del lenguaje: operadores aritméticos y lógicos nativos, tipos primitivos del CLR (System.Int64, System.Double) y reglas de promoción numérica (ECMA-334 §10.2.3).
  • Tiempo de compilación: resolución de nombres, verificación de tipos estáticos, selección de sobrecargas y análisis estático de nulabilidad.
  • Tiempo de ejecución (JIT / CLR): despacho dinámico de interfaces (IRpnOperation.Apply vía tabla de métodos virtuales) y, en el intérprete RPN, enlace dinámico de variables del usuario en SymbolEnvironment.

En un evaluador estrictamente postfijo, al leer el primer token de expresiones como x 10 = o x x 1 + = aún no se conoce si x actuará como valor (R-value) o como destino de asignación para = (L-value, incluso antes de existir). Aplicando la distinción clásica de Strachey, el tipo algebraico StackSlot modela ambos roles en la pila:

src/RpnRepl/Types/StackSlot.csL-value vs. R-value en pila
public abstract record StackSlot
{
    private StackSlot() { }

    public sealed record ValueSlot(RpnValue Value) : StackSlot;

    public sealed record SymbolSlot(
        string Name,
        RpnValue? CapturedValue,
        int? ScopeDepth,
        SourceSpan Span) : StackSlot;
}

Si la variable existe al leer el token, SymbolSlot captura su valor actual (CapturedValue) como R-value inmediato y conserva su Name por si un operador = posterior la consume como L-value. Si no existe (CapturedValue == null) y ningún = la enlaza al concluir la línea, FindDanglingUndefinedSymbol la detecta y retorna RpnError.UndefinedVariable tras revertir transaccionalmente la pila.

1.3 Estructuras de Control y Contexto Aritmético checked

Además de las estructuras imperativas clásicas (ECMA-334 §13: if/switch, while/for/foreach), C# incorpora expresiones switch funcionales con pattern matching posicional, de tipo y relacional. En RpnEvaluator.cs y ArithmeticOperation coexisten un bucle foreach imperativo para recorrer tokens y expresiones switch junto a bloques checked { ... }.

Detalle de Especificación: Aritmética checked vs. unchecked (ECMA-334 §12.8.20)
Por defecto en C#, la aritmética entera opera en contexto unchecked (desbordamiento silencioso en complemento a dos). En ArithmeticOperation.ApplyInt se emplea explícitamente un bloque checked { ... } para que desbordamientos como 9223372036854775807 1 + lancen OverflowException, la cual se captura y traduce a RpnError.ArithmeticOverflow sin interrumpir la sesión del REPL.

1.4 Reglas de Alcance (Scoping) y Shadowing: C# frente al Mini-REPL

C# implementa alcance léxico (estático) por bloques delimitados por llaves { ... } (§7.6). Como regla de seguridad, el compilador prohíbe el shadowing de variables locales en bloques anidados dentro de un mismo método (error CS0136), evitando ocultamientos accidentales; en cambio, sí permite sombrear campos de instancia mediante parámetros o locales desambiguables con this..

Para satisfacer los bloques temporales begin ... end en el Mini-REPL, SymbolEnvironment mantiene una cadena enlazada de marcos ScopeFrame con búsqueda ascendente hacia el alcance padre y escritura estricta en el marco más interno (_currentScope.BindLocal). Así, toda variable definida o modificada dentro de begin ... end genera shadowing temporal y desaparece al ejecutar end sin alterar las variables homónimas globales.

2. Sistema de Tipos de Datos y Chequeo de Tipos

2.1 El Common Type System (CTS) y Emulación de ADTs Cerrados en C# 12

El sistema de tipos de C# (ECMA-334 §8) se apoya en el Common Type System (CTS) unificado del CLR, donde los tipos se dividen en tipos por valor (struct, enum, readonly record struct) y tipos por referencia (class, record class, interface, delegados), con genéricos reificados en tiempo de ejecución sin borrado de tipos.

Para modelar valores, tokens y errores del evaluador (Requisito #2), C# permite implementar Tipos Algebraicos de Datos (ADTs / Sum Types) mediante una jerarquía cerrada de abstract record con constructor private y variantes internas sealed record:

src/RpnRepl/Types/RpnValue.cs & Diagnostics/RpnError.csADTs cerrados en C# 12
public abstract record RpnValue
{
    private RpnValue() { }  // Impide herencia externa: suma cerrada de variantes

    public sealed record IntValue(long Value) : RpnValue { ... }
    public sealed record FloatValue(double Value) : RpnValue { ... }
    public sealed record BoolValue(bool Value) : RpnValue { ... }
}

2.2 Chequeo Estático, Flujo Nulo, Inferencia y Chequeo Dinámico del Evaluador

La verificación de tipos se articula en dos niveles complementarios:

  1. Chequeo estático y seguridad de nulos en C# (Roslyn): C# es estática y fuertemente tipado (no existe coerción implícita bool → int). Con <Nullable>enable</Nullable> y <TreatWarningsAsErrors>true</TreatWarningsAsErrors>, el compilador valida estáticamente la nulabilidad; en EvalResult<T>, los atributos [NotNullWhen(true)] y [NotNullWhen(false)] garantizan al compilador qué parámetro out queda inicializado como no nulo en cada rama.
  2. Inferencia de tipos: se limita al ámbito local mediante var (resuelto estáticamente en compilación, distinto de dynamic), expresiones new(...) inferidas por tipo destino y expresiones de colección [...].
  3. Chequeo dinámico del Mini-REPL (TypeChecker.cs): en tiempo de evaluación de la pila, las operaciones distinguen entre Int (Int64), Float (Double) y Bool: Int con Int produce Int (incluyendo división entera 7 2 / → 3), la combinación con Float promueve a Float (análoga a ECMA-334 §10.2.3), y cualquier mezcla inválida con Bool (como 5 true + o 5 true ==) retorna RpnError.TypeMismatch.
src/RpnRepl/Engine/TypeChecker.csPromoción numérica y rechazo de Bool
public static EvalResult<NumericOperands> PromoteNumericPair(
    string operatorSymbol, RpnValue left, RpnValue right, in SourceSpan span) =>
    (left, right) switch
    {
        (RpnValue.IntValue a, RpnValue.IntValue b)     => EvalResult<NumericOperands>.Ok(new NumericOperands.IntPair(a.Value, b.Value)),
        (RpnValue.FloatValue a, RpnValue.FloatValue b) => EvalResult<NumericOperands>.Ok(new NumericOperands.FloatPair(a.Value, b.Value)),
        (RpnValue.IntValue a, RpnValue.FloatValue b)   => EvalResult<NumericOperands>.Ok(new NumericOperands.FloatPair(a.Value, b.Value)),
        (RpnValue.FloatValue a, RpnValue.IntValue b)   => EvalResult<NumericOperands>.Ok(new NumericOperands.FloatPair(a.Value, b.Value)),
        _ => EvalResult<NumericOperands>.Fail(
            new RpnError.TypeMismatch(operatorSymbol, left.TypeName, right.TypeName, "(Int|Float, Int|Float)", span))
    };

2.3 Equivalencia Nominal, Igualdad Estructural y Comparativa de Lenguajes

La equivalencia de tipos en C# es nominal: dos class, struct o record con campos idénticos pero nombres distintos no son intercambiables sin conversión explícita (a diferencia del tipado estructural de TypeScript o interfaces de Go). No obstante, los record y readonly record struct sintetizan igualdad estructural por valor (Equals, ==, GetHashCode), facilitando aserciones directas sobre valores y copias no destructivas mediante with.

3. Subrutinas, Mecanismos de Paso de Parámetros y Manejo de Memoria

3.1 Subrutinas y Paso de Parámetros en C# (ECMA-334 §15.6.2)

C# ofrece control explícito sobre la transferencia de copias, referencias mutables y préstamos de solo lectura. En RpnEvaluator, la pila (EvaluationStack) y la tabla de símbolos (SymbolEnvironment) se pasan explícitamente a cada subrutina para evidenciar cada modalidad:

3.2 Gestión de Memoria: Stack, Managed Heap, ref struct y Garbage Collector

El CLR separa la memoria en el Stack de hilo (asignación y liberación determinista al entrar y salir de cada marco de llamada) y el Managed Heap (administrado por un Recolector de Basura generacional de tres generaciones: Gen 0, Gen 1 y Gen 2, compacto y libre de errores de liberación manual).

Para evitar asignaciones innecesarias al Heap durante el escaneo léxico, SpanTokenScanner se define como ref struct con un campo ReadOnlySpan<char>. El compilador restringe todo ref struct exclusivamente al Stack (prohibiendo boxing a object, almacenamiento en campos de clases o captura en lambdas), por lo que segmentar tokens por espacios no genera arreglos ni subcadenas intermedias.

4. Abstracción de Datos y Conceptos de Programación Orientada a Objetos

4.1 Encapsulación, Modificadores de Acceso e Invariantes

La encapsulación en C# (ECMA-334 §7.5) regula la visibilidad con public, private, protected, internal y propiedades init. En EvaluationStack y ScopeFrame, las colecciones mutables subyacentes (List<StackSlot> y Dictionary<string, RpnValue>) son private readonly. Las subrutinas externas solo acceden mediante vistas de solo lectura (IReadOnlyList<StackSlot>, IReadOnlyDictionary<string, RpnValue>) o la interfaz segregada IScopeLookup, preservando los invariantes de pila y alcance.

4.2 Interfaces vs. Clases Abstractas: Polimorfismo Abierto y Composición

C# separa la herencia simple de clases de la implementación múltiple de interfaces (ECMA-334 §19). El diseño del evaluador combina ambas estrategias según la naturaleza de cada componente:

  • Polimorfismo abierto mediante interfaces y composición (IRpnOperation, IOperationRegistry): desacopla la implementación de operadores (ArithmeticOperation, ComparisonOperation) del motor RpnEvaluator(IOperationRegistry operations) mediante inyección de dependencias en su constructor primario.
  • Polimorfismo cerrado mediante abstract record (Token, RpnValue, RpnError): modela dominios cerrados donde las variantes son fijas y se manipulan mediante pattern matching.

5. Verificación Práctica y Sesión Demostrativa del Mini-REPL

El evaluador implementa estrictamente el algoritmo de pila LIFO para Notación Polaca Inversa (sin paréntesis y preservando el orden relativo de operandos: en operadores no conmutativos como - y /, TryPopTwoRValues extrae el tope como operando derecho y el inmediato inferior como izquierdo, evaluando 10 2 - → 8 y 15 7 1 1 + - / 3 * 2 1 1 + + - → 5). El comportamiento completo fue validado mediante pruebas unitarias automatizadas con xUnit y ejecución interactiva del intérprete.
