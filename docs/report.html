1. Nombres, Vinculación (Binding), Estructuras de Control y Alcance (Scoping)

1.1 Nombres, Palabras Reservadas e Identificadores

De acuerdo con la especificación de C# (ECMA-334, Cap. 6), los identificadores son sensibles a mayúsculas y minúsculas (case-sensitive), admiten caracteres Unicode de categorías de letras y guion bajo inicial, y distinguen estrictamente entre palabras clave reservadas (como class, struct, ref, in, out, switch) y palabras clave contextuales (como record, init, var, required). Estas últimas permitieron la evolución del lenguaje hacia características modernas sin romper compatibilidad con código legado que usara dichos nombres como identificadores.

En el Mini-REPL, el analizador léxico SpanLexer replica una gramática léxica limpia al evaluar el lexema en orden determinista: primero verifica operadores y palabras clave del lenguaje RPN (true, false, begin, end) mediante pattern matching directo sobre ReadOnlySpan<char>, luego literales numéricos y finalmente identificadores válidos que comiencen por letra o _.

1.2 Tiempos de Vinculación (Binding Times) y Semántica L-value vs. R-value

C# es un lenguaje predominantemente de vinculación estática (en tiempo de compilación mediante Roslyn), pero combina múltiples instantes de enlace según la construcción:

  • Tiempo de diseño del lenguaje: los operadores nativos (+, /), los tipos primitivos del CLR (System.Int64, System.Double) y las reglas de promoción numérica (ECMA-334 §10.2.3).
  • Tiempo de compilación: resolución de nombres, verificación de tipos estáticos, sobrecarga de operadores, despacho de métodos de extensión y análisis de flujo nulo (null-state static flow analysis).
  • Tiempo de ejecución (JIT / CLR): despacho dinámico de implementaciones de interfaz (IRpnOperation.Apply mediante tabla virtual / vtable) y, a nivel del dominio RPN, resolución de variables del usuario en SymbolEnvironment.

Un desafío clásico en un evaluador postfijo estricto ocurre al procesar expresiones como x 10 = o x x 1 + =: cuando aparece x al inicio, el evaluador aún no sabe si x será leído como valor (R-value) o si será el destino izquierdo de una asignación = (L-value, incluso cuando x todavía no existe). Siguiendo la distinción clásica de Strachey, nuestro diseño resuelve este problema mediante el tipo algebraico StackSlot:

src/RpnRepl/Types/StackSlot.csL-value vs. R-value en pila
public abstract record StackSlot
{
    private StackSlot() { }

    public sealed record ValueSlot(RpnValue Value) : StackSlot;

    public sealed record SymbolSlot(
        string Name,
        RpnValue? CapturedValue,
        int? ScopeDepth,
        SourceSpan Span) : StackSlot;
}

Si x ya existía al momento de leer el token, SymbolSlot captura su valor actual (CapturedValue) como R-value inmediato, conservando simultáneamente su Name por si un operador = posterior lo consume como L-value. Si no existía (CapturedValue == null) y ningún = lo consume al finalizar la línea, FindDanglingUndefinedSymbol lo detecta y reporta RpnError.UndefinedVariable tras revertir transaccionalmente la pila.

1.3 Estructuras de Control y Contexto Aritmético checked

C# ofrece estructuras de control imperativas clásicas (ECMA-334 §13: selección if/switch, iteración while/for/foreach), pero desde C# 8 incorpora expresiones switch orientadas a expresiones con verificación de exhaustividad y patrones posicionales, de tipo y relacionales. En RpnEvaluator.cs y ArithmeticOperation se combinan ambos enfoques: un bucle foreach imperativo para recorrer el flujo de tokens junto a expresiones switch funcionales y bloques checked { ... }.

Matiz de Diseño de C#: Aritmética checked vs. unchecked (ECMA-334 §12.8.20)
Por defecto en C#, las operaciones enteras se ejecutan en contexto unchecked (desbordamiento silencioso en complemento a dos por rendimiento). En ArithmeticOperation.ApplyInt usamos explícitamente un bloque checked { ... } para que operaciones como 9223372036854775807 1 + disparen OverflowException, capturada inmediatamente y transformada en un valor RpnError.ArithmeticOverflow sin abortar el REPL.

1.4 Reglas de Alcance (Scoping) y Shadowing: C# vs. el Mini-REPL

C# aplica alcance léxico (estático) por bloques delimitados por llaves { ... } (§7.6). Una regla de diseño notable del compilador de C# es que prohíbe el shadowing de variables locales en bloques anidados dentro del mismo método (error CS0136: A local or parameter named 'x' cannot be declared in this scope because that name is used in an enclosing local scope), previniendo errores accidentales de captura o confusión, mientras que sí permite sombrear campos de clase mediante parámetros o locales (desambiguados con this.).

En contraste, para cumplir el requisito de bloques temporales (begin ... end) del Mini-REPL, SymbolEnvironment implementa una cadena enlazada de marcos ScopeFrame con búsqueda ascendente (del marco más interno al global) y vinculación local en escritura: toda asignación dentro de un bloque begin escribe exclusivamente en el marco más interno (_currentScope.BindLocal), generando shadowing temporal y garantizando que al ejecutar end el entorno global permanezca inalterado.

2. Sistema de Tipos de Datos y Chequeo de Tipos

2.1 El Common Type System (CTS) y Emulación de ADTs Cerrados en C# 12

El sistema de tipos de C# (ECMA-334 §8) se fundamenta en el Common Type System (CTS) unificado del CLR, donde prácticamente todo tipo hereda directa o indirectamente de System.Object (permitiendo genéricos reales sin borrado de tipos, a diferencia de Java). Sus categorías principales se dividen en tipos por valor (struct, enum, readonly record struct) y tipos por referencia (class, record class, interface, delegados).

Para representar los valores, tokens y errores del evaluador (Requisito #2), C# permite construir Tipos Algebraicos de Datos (ADTs / Sum Types) mediante una jerarquía cerrada de abstract record con constructor private y variantes internas sealed record:

src/RpnRepl/Types/RpnValue.cs & Diagnostics/RpnError.csADTs cerrados en C# 12
public abstract record RpnValue
{
    private RpnValue() { }  // Impide herencia fuera de la clase: suma cerrada

    public sealed record IntValue(long Value) : RpnValue { ... }
    public sealed record FloatValue(double Value) : RpnValue { ... }
    public sealed record BoolValue(bool Value) : RpnValue { ... }
}

2.2 Chequeo Estático, Flujo Nulo, Inferencia y Chequeo Dinámico del Evaluador

El chequeo de tipos en nuestro proyecto opera en dos niveles complementarios:

  1. Chequeo estático en C# (Roslyn) con seguridad de nulos: C# es estáticamente tipado y fuertemente tipado (no existen conversiones implícitas arbitrarias como bool → int). Activando <Nullable>enable</Nullable> y <TreatWarningsAsErrors>true</TreatWarningsAsErrors>, el compilador realiza análisis de flujo estático para garantizar ausencia de desreferencias nulas. En EvalResult<T>, los atributos [NotNullWhen(true)] y [NotNullWhen(false)] comunican al compilador exactamente qué parámetro out es no nulo en cada rama del if.
  2. Inferencia de tipos local y contextual: C# combina tipado estático explícito en firmas públicas con inferencia local mediante var (el tipo se resuelve íntegramente en compilación, nunca es dinámico como dynamic), expresiones new(...) inferidas por destino (target-typed new) y expresiones de colección [...].
  3. Chequeo dinámico en tiempo de ejecución del Mini-REPL (TypeChecker.cs): Como el lenguaje RPN interpretado carece de anotaciones de tipo en su sintaxis de entrada, el evaluador realiza verificación de tipos en tiempo de ejecución sobre las variantes de RpnValue. Las reglas replican la disciplina estricta de C#:
    • Int + Int → Int (incluyendo división entera 7 2 / → 3 : Int, igual que C# int / int).
    • Int mezclado con Float → Float (promoción numérica segura sin pérdida de dominio, análoga a ECMA-334 §10.2.3).
    • Operaciones con Bool en aritmética o desigualdad de orden (5 true +, true false <) o igualdad heterogénea (5 true ==) se rechazan mediante RpnError.TypeMismatch.
src/RpnRepl/Engine/TypeChecker.csPromoción numérica y rechazo de Bool
public static EvalResult<NumericOperands> PromoteNumericPair(
    string operatorSymbol, RpnValue left, RpnValue right, in SourceSpan span) =>
    (left, right) switch
    {
        (RpnValue.IntValue a, RpnValue.IntValue b)     => EvalResult<NumericOperands>.Ok(new NumericOperands.IntPair(a.Value, b.Value)),
        (RpnValue.FloatValue a, RpnValue.FloatValue b) => EvalResult<NumericOperands>.Ok(new NumericOperands.FloatPair(a.Value, b.Value)),
        (RpnValue.IntValue a, RpnValue.FloatValue b)   => EvalResult<NumericOperands>.Ok(new NumericOperands.FloatPair(a.Value, b.Value)),
        (RpnValue.FloatValue a, RpnValue.IntValue b)   => EvalResult<NumericOperands>.Ok(new NumericOperands.FloatPair(a.Value, b.Value)),
        _ => EvalResult<NumericOperands>.Fail(
            new RpnError.TypeMismatch(operatorSymbol, left.TypeName, right.TypeName, "(Int|Float, Int|Float)", span))
    };

2.3 Equivalencia Nominal, Igualdad Estructural y Comparativa de Lenguajes

En C#, la equivalencia de tipos es estrictamente nominal: dos class, struct o record distintos con exactamente los mismos campos no son asignables entre sí sin conversión explícita (a diferencia del tipado estructural de TypeScript o Go con interfaces implícitas). No obstante, los tipos record y readonly record struct generan automáticamente igualdad de valores estructural (Equals, ==, GetHashCode), lo que nos permite comparar resultados en pruebas con Assert.Equal(new RpnValue.IntValue(30), report.TopValue) y usar expresiones no destructivas with en SymbolEnvironment.

3. Subrutinas, Mecanismos de Paso de Parámetros y Manejo de Memoria

3.1 Subrutinas y Paso de Parámetros en C# (ECMA-334 §15.6.2)

C# dispone de uno de los conjuntos más expresivos de mecanismos de paso de parámetros entre los lenguajes orientados a objetos gestionados, permitiendo controlar con precisión si se transfiere una copia, un puntero administrado modificable o un préstamo de solo lectura. En RpnEvaluator, la pila (EvaluationStack) y la tabla de símbolos (SymbolEnvironment) se pasan explícitamente a cada subrutina para demostrar todos los modos:

3.2 Gestión de Memoria: Stack, Managed Heap, ref struct y Garbage Collector

El CLR divide la memoria de ejecución en el Stack de hilo (asignación y liberación determinista O(1) al entrar y salir de cada marco de llamada) y el Managed Heap (administrado por un Recolector de Basura generacional de tres generaciones: Gen 0, Gen 1 y Gen 2, compacto y sin necesidad de free/delete manuales ni aritmética insegura de punteros fuera de bloques unsafe).

Para minimizar la presión sobre el GC durante el análisis léxico, SpanTokenScanner se declara como ref struct conteniendo un campo ReadOnlySpan<char>. En C#, un ref struct tiene garantizada por el compilador su permanencia exclusiva en el Stack: no puede ser convertido a object (boxing), no puede ser campo de una class ni capturado en clausuras lambda. De este modo, segmentar expresiones separadas por espacios no asigna arreglos de subcadenas intermedios en el Heap.

4. Abstracción de Datos y Conceptos de Programación Orientada a Objetos

4.1 Encapsulación, Modificadores de Acceso e Invariantes

La encapsulación en C# (ECMA-334 §7.5) controla la visibilidad mediante public, private, protected, internal y propiedades de solo inicialización (init). En EvaluationStack y ScopeFrame, las colecciones subyacentes mutables (List<StackSlot> y Dictionary<string, RpnValue>) son estrictamente private readonly. Las subrutinas externas solo pueden inspeccionar la memoria mediante proyecciones de solo lectura (IReadOnlyList<StackSlot>, IReadOnlyDictionary<string, RpnValue>) o a través de la interfaz segregada IScopeLookup, impidiendo mutaciones fuera de protocolo (como alterar la profundidad de alcance sin pasar por begin/end).

4.2 Interfaces vs. Clases Abstractas: Polimorfismo Abierto y Composición

C# separa limpiamente la herencia simple de implementación (una clase solo hereda de una superclase) de la implementación múltiple de interfaces (ECMA-334 §19). Nuestro evaluador aprovecha esta dualidad siguiendo un criterio arquitectónico clásico en diseño de compiladores e intérpretes:

  • Polimorfismo abierto basado en interfaces y composición (IRpnOperation, IOperationRegistry): Permite definir operaciones independientes (ArithmeticOperation, ComparisonOperation) e inyectar un IOperationRegistry personalizado en el constructor primario de RpnEvaluator(IOperationRegistry operations) sin alterar el motor de evaluación.
  • Polimorfismo cerrado basado en abstract record (Token, RpnValue, RpnError): Cuando la familia de datos es fija y las operaciones sobre ella evolucionan (Expression Problem), una jerarquía cerrada de registros permite pattern matching conciso y seguro.
